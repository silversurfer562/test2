# Plan: Deletion, proven end to end

**Spec**: [attune-rag/docs/specs/provable-deletion/](../../docs/specs/provable-deletion/)
**Created**: 2026-09-11

---

## Summary

The brief says attune-rag has no way to remove a document. It has one, and that is worse. `attune-rag/src/attune_rag/editor/rename.py::apply_rename` (line 436) is a shipping, public, two-phase mutating operation over a corpus: it moves template files with `os.replace`, rewrites the path-keyed `summaries.json` / `summaries_by_path.json` sidecars (`_PATH_KEYED_SIDECARS`, line 43), rolls back every phase on a mid-flight failure, and then calls `_refresh_corpus(corpus)` at line 624 to invalidate. That function is five lines long and reads `for attr in ("_loaded", "_aliases"): setattr(corpus, attr, None)`. It cannot reach `EmbeddingRetriever._cache`, which is a `dict[int, ...]` keyed by `id(corpus)` and written at `attune-rag/src/attune_rag/embedding.py` lines 125 and 132. The brief's grep returned nothing because it was scoped to `corpus/`, `retrieval.py` and `embedding.py`; `editor/` was outside the window. The real finding is that mutation already ships and its invalidation is incomplete, which is a defect that can be made red today rather than a feature that has to be imagined first.

Three more code facts change the design. **The `id(corpus)` key is unsound, not merely un-invalidatable.** The cache holds strong references to the entries list and the matrix and no reference to the corpus itself, so nothing keeps the keyed object alive; CPython recycles `id()` after collection, and a new corpus allocated at a freed address silently inherits the dead corpus's embedding matrix. That is a cross-corpus content leak, and it is the strongest argument in the program for the invalidation surface being asked for. **`DirectoryCorpus.version` is not a complete content fingerprint.** Lines 380-387 hash only the entry key and `entry.content`; `summary`, `aliases`, `related` and `metadata` are excluded. `EmbeddingRetriever._entry_text` embeds `entry.summary`, so a sidecar-only mutation — a rewritten `summaries.json` or `cross_links.json`, which is exactly what `apply_rename` does by design — leaves `version` unchanged. Any cache token built on `version` alone therefore trades one staleness for another, and the fingerprint has to be widened in the same change. **The alias dangling-pointer claim is backwards.** `DirectoryCorpus._build` (lines 221-280) consults every sidecar by looking *up* from a file found on disk, so a summary or alias override for a path that no longer exists is never read — silently inert, not dangling, and it surfaces no retrieval error ever. `alias_index` and the entries are produced in one pass and cannot diverge. The dangling alias is a regression the new API would introduce, not a defect to be fixed. The same is true of the second entry token cache: `retrieval.py` line 291 keys `("related_tokens", corpus.name)`, and `DirectoryCorpus.name` is constant across every mutation, but the cache lives on the frozen `RetrievalEntry` object and today every mutation path rebuilds those objects — `_refresh_corpus` nulls `_loaded`, `_ensure_loaded` (line 329) re-runs `_build`, and fresh entries start with an empty `_tokens_cache` (`base.py` line 59). `_related_summary_tokens`'s own docstring says so verbatim. That cache is a regression an in-place `remove()` would introduce, and T3 carries a standing guard against it rather than T2 carrying a red case that cannot be red. The one sidecar that genuinely dangles is `cross_links.json`: `RetrievalEntry.related` keeps the removed path as a string, `_related_summary_tokens` gets `None` from `corpus.get()` and skips it at lines 297-299 with no error and no warning — a quiet loss of the related-hits signal on every surviving neighbour.

On the attune-ai side, three of the brief's five layers do not exist. There is no graph: `memory-unification` D1 (LOCKED 2026-07-04) removed the middle layer entirely, `MemoryGraph` and friends were deleted in 10.0.0, and `tests/unit/memory/test_removed_graph_shim.py` asserts that touching them raises `AttributeError` matching "removed in 10.0.0". There is no git-backed store: `promotion.default_curated_dir()` returns `~/.attune/memory/curated` and no code in the package performs any git operation on it; it is git-backed only because the user's `~/.attune/memory` happens to be a pushed repository, which is `memory-unification` OQ1 reason 1 and lives outside all four in-scope repos. And FCALL `recall_digest` is not here either — there is no `.lua` file anywhere in attune-ai, `recall_digest.py` lines 32-33 name the function's home as the memory repo's `functions.lua`, and `hydrate.py` is loaded by `tests/unit/memory/test_session_hydrate_stale_stamp.py` through `spec_from_file_location` with an explicit skip when the external checkout is absent. What does exist is better than the brief's description: `verdict_log.propagate_verdict(stem, client)` at line 217 already deletes the derived Redis key `attune:memory:node:<stem>` immediately, best-effort, logging at WARNING with the exception type so a propagation regression stays visible, and `PersonalMemory.forget_topic` (personal.py line 420) already does store-plus-derived removal correctly — `_remove_from_summaries` before every unlink, under `file_lock`, through `atomic_write_text`. This plan calls both rather than reinventing either.

The surface list for a promoted curated node is smaller than the brief assumes, and the difference decides whether the gate is real or vacuous. `promote()` (promotion.py line 142) writes exactly one `.md` file and touches nothing else: it writes no `MEMORY.md` pointer — `curated_audit._pointer_integrity` (line 626) says so in its own docstring at line 637, "attune's own curated store is exactly that shape" — and it writes no `summaries_by_path.json` key, because the only writer of that sidecar in the package is `PersonalMemory._update_summaries` (personal.py line 516) on the remember path. An erasure test that promotes a node and then asserts those two surfaces are absent passes on unmodified main with no erasure code at all. Both legs are kept, because a user who authors a `MEMORY.md` in the curated directory or who reaches a curated node through `remember()` does produce them — but T6 seeds each surface explicitly and asserts PRESENT before and ABSENT after, one paired assertion per surface, so every leg can fail.

The hardest correction is a collision, not an omission. "Delete a curated node and assert it is gone" runs straight into `memory-status-integrity` D6 (decisions.md line 254, item 3 at line 281), recorded in `verdict_log.py`'s own module docstring: wrong verdicts **tombstone, never delete**, because deletion breaks MEMORY.md pointers and `[[links]]`, and "we believed X, it was wrong" is itself high-value memory — the log is append-only precisely so a thoughtless bulk decision cannot be hidden. That is the brief's key trap pointed the other way. Two operations are being conflated, and T1/T1a separate them before any code is written: a review verdict of `wrong` tombstones and the node stays, marked; user-initiated erasure genuinely deletes everywhere. Only erasure can carry the claim, and only erasure is gated here.

Shipping this converts one claim from asserted to checkable: that a removed document stops being retrievable through every path in the package, and that an erased curated memory stops being answerable through the file, the summaries sidecar, any authored MEMORY.md pointer, the serve-telemetry frequency signal and the derived Redis node. Three limitations are conceded at full strength and published with the claim rather than beside it. First, the digest and hydration legs are external. FCALL `recall_digest` and `hydrate.py` live in the `~/.attune/memory` checkout, and the only in-repo digest surface, `render_digest_html`, is a pure transform over nodes a fake client hands it — it can be made green with no erasure code at all, so it is a receipt in `docs/specs/curated-erasure/receipts.md`, not a CI leg, and T6 and T7 say so. Second, erasure leaves a deliberate audit record — a stem and a content digest, no content — in `.verdicts.jsonl`, because D6 makes that log append-only and because a deletion nobody can audit is its own failure mode. Third, `ConversationSummaryIndex` is Redis-backed short-term state with `DEFAULT_TTL = 86400` (summary_index.py line 144), keyed `empathy:summary:<session_id>` / `empathy:timeline:<session_id>` / `empathy:topic:<topic>`, and nothing in `src/` constructs it today. A session summary written before the `curated_sources` back-reference existed may still quote an erased memory verbatim in the timeline zset for **up to 24 hours**, after which it expires. That is the honest boundary — not "unreachable forever" — and T5 adds the back-reference plus a reverse index going forward so the window closes. A memory removed from the store but surviving in a summary is not deleted, it is hidden, and hidden is worse because the claim then reads as true.

## Reference

**How paths in this plan resolve.** Every path is rooted at the workspace directory holding `attune-rag/`, `attune-ai/`, `attune-verify/` and `attune-forms/` as siblings, and the runner's working directory is that root. There is no bare-relative form and no `../` prefix. This matters mechanically, not stylistically: attune's runner resolves the strings in `path="..."` against the process CWD (`pipeline/orchestrator.py::_run_quality_gate`, `_find_test_files`, `_get_source_files`, `_run_tests`), `_find_test_files` maps a path to its test only when it starts `src/attune/` while `_get_source_files` has no such guard, and `read_spec` discards everything outside `<task>` blocks — so a base-directory rule stated only in this section would never reach the runner. It is therefore restated verbatim inside T1's `<objective>`, which is prose the parser preserves. attune-rag has no `.claude/plans/` directory, and none of the 45 plans in `attune-ai/.claude/plans/` uses a `../` prefix inside a `path` attribute, so there is no house convention to inherit either way.
